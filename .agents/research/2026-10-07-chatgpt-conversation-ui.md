# ChatGPT 对话展示调研与 emu-chat 对照

调研日期：2026-10-07。范围：工具调用、助手回复操作、生成图片及相关阅读体验。本记录用于方案讨论，相关设计已整理为 proposed 提案，尚未实施。

## 证据范围

本次通过 OpenAI Docs 流程检索并读取官方公开文档，查看官方 UI 指南配图，并对照 emu-chat 当前源码与现行决定。没有进入 ChatGPT 登录态网页实测，也没有运行 emu-chat 的交互截图验证。官方配图主要是移动端插件示例，不能当作当前网页版每个原生控件的精确规格。复制按钮位置、悬停显隐、生成动画等未由本次材料直接确认，以下相关内容均是针对本项目的建议。

可确认的参考：

- [官方 UI 指南](https://developers.openai.com/plugins/concepts/ui-guidelines)：工具名称与轻量内容可以嵌入对话，卡片应控制主要操作数量；配色、字号和间距保持克制与一致，复杂内容可进入更大的展示空间。该指南针对插件 UI，不能直接当成原生工具调用的完整规范。
- [官方内联示例图](https://developers.openai.com/images/apps-sdk/inline_display_mode.png)与[卡片布局图](https://developers.openai.com/images/apps-sdk/inline_card_layout.png)：图片或地图成为结果主体，说明文字与操作围绕结果组织。图片不是一律按附件缩略图处理。
- [官方图片文档](https://learn.chatgpt.com/docs/image-generation)：生成图片可进入扩展查看器；文档区分单图查看与同一聊天的图片集合查看。这些模式的具体可用性随界面与账号变化，emu-chat 首期可以只借鉴点击放大。

## 项目现状

| 区域 | 源码确认的现状 | 优化机会 |
| --- | --- | --- |
| 工具调用 | 每次调用一个带边框的折叠框，标题保留真实工具名和状态；展开显示脱敏输入及输出，错误默认展开。 | 减少连续调用的边框、胶囊和垂直占用，强化运行与异常状态。 |

| 代码块 | 普通代码有复制及成功反馈；可预览代码以“打开预览”取代复制入口。 | 同时保留复制代码与预览，统一失败反馈。 |

| 辅助信息 | 助手有头像、角色名、时间和运行操作，工具状态使用强调色。 | 历史回复减少元信息存在感，把视觉重点放在正文和结果。 |

## 建议一：工具过程轻量化

保留工具名与状态，用一条紧凑、可展开的过程行代替默认厚卡片。运行时显示小型活动指示，成功用低对比度状态，失败保留醒目错误并默认展开。标题继续不显示命令摘要，遵守[已有工具名决定](../notes/implemented/feature/2026-09-25-tool-name-only-card-header.md)。

展开后保持输入、输出的清晰标签；长输出先截断，用户主动查看完整内容，避免一打开就占满屏幕。复制输入/输出属于次要操作，不常驻一排大按钮。

仅将相邻、已完成的普通工具调用合成“已完成 3 次工具调用”这类可展开列表。正文穿插处、生图结果、错误、审批和待核对步骤保持原位。不能把过程全部搬到回复顶部，否则会退回已经解决的重排问题。分组属于后续增强，第一步只改每条过程行，降低交接和展开状态丢失的风险。

## 建议二：助手回复复制与代码操作

每个助手回合底部增加小型操作区，首期以复制为主。最近回复的入口容易发现，历史回复可在悬停或键盘聚焦时加强显示；触屏必须有直接可用的入口。按钮需要可读标签、成功勾选与“已复制”提示，以及失败提示。

建议默认复制该回合可见的助手文字，按展示顺序组合，保留 Markdown 和代码围栏；不包括思考、工具原始输入输出、状态提示、文件机器清单和界面按钮。复制代码块则只复制代码原文。流式阶段可以等回合结束后开放普通复制，避免用户误以为已经复制完整回复；停止后的已有文本仍可复制。

可预览代码同时提供“复制代码”和“打开预览”。普通回复复制与工具详情复制各自独立，避免一键复制夹带调试日志。失败时不得显示成功；局域网 HTTP 下要考虑 Clipboard API 不可用的手动选中备用方式。

## 建议三：生成图片作为主要结果

生成结果采用单独的展示布局，不把上传附件样式全局放大。建议桌面单图初始最大宽度约 400–480px，窄屏按可用宽度缩放；保留原图比例，限制过高图片对阅读的占用，不裁切原件。多图使用两列或自适应网格，避免极小缩略图挤成一排。这些尺寸是本项目设计起点，不是 ChatGPT 测量值。

已明确识别生图工具开始时显示有尺寸的占位区域；有尺寸信息则按真实比例，无信息使用保守默认框。状态文案应根据真实状态区分：正在生成 → 正在保存图片 → 已就绪；另有生成失败、保存失败、暂不可用、等待核对。使用不定进度的轻动画，不编造百分比、剩余时间或逐步清晰的预览。收到权威图片结果后尽量在同一位置替换占位，保留实时与历史交接的稳定性。

卡片旁直接提供“下载”和“用于下一条消息”，无需先打开查看器；点击图片继续使用现有大图查看器。桌面操作可在悬停/聚焦时呈现，触屏保持可访问。技术输入输出折叠为详情，图片结果不随工具详情一起隐藏。透明底棋盘仅用于确有透明通道的预览情境；普通图片等待区使用中性背景。

“重试保存”沿用现有采集接口，不重新调用生图模型。重新生成若将来加入，应作为明确的新请求，不能与保存重试共用入口。现有 SSE 没有稳定工具调用 ID，同名并发仍不得猜测哪张图属于哪次调用；不确定时保留待核对提示，依权威历史配对。

## 其他可借鉴的改进

- 降低角色名、时间和历史成功状态的对比度；为正文、代码、工具详情、图片建立一致的间距节奏。
- 代码块同时提供复制与预览；长表格和长代码局部横向滚动，保持正文宽度，避免整个对话横向溢出。
- 状态动画只用于当前活动内容，遵守减少动画偏好；成功、错误和等待状态不能仅靠颜色辨认。
- 统一图标按钮的悬停、聚焦、禁用与成功反馈，确保窄屏和触屏可用。

## 建议的安排

三个展示方向分别形成提案，便于选择范围及回归验证：助手回复与代码复制、工具调用展示、生成图片结果卡片。复制的成本较低、效果直接；工具行轻量化其次；图片优化的视觉收益最大，但需要更细的生成/采集/历史核对状态衔接。用户随后反馈手机 Edge 的输入区占用过多阅读空间，因此补充第四个提案，建议优先解决手机输入区的空间与视口问题。

本轮范围为对话展示与手机输入区，不同时大改侧栏或引入新的 UI 框架。正式实施时，用工具密集回合、普通长回复、代码预览、单图/多图及图片保存失败制作本地交互样例，检查深浅主题、窄屏和实时交接；手机输入区还需验证软键盘、地址栏和横竖屏切换。无需发起真实付费模型请求。
