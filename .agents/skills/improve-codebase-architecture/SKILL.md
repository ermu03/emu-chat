# 评估架构改进

先按用户指定的模块或痛点确定范围；没有指定时，从近期改动和实际维护摩擦选择范围。阅读相关源码、项目文档、AGENTS.md 和同主题决策笔记。参考 codebase-design 的模块设计原则，但不要求另起代理或生成报告文件。

只提出能指向具体代码和成本的候选：例如队列或 Run 规则分散、Hermes 协议细节泄漏、SQLite 事务责任不清、客户端状态重复维护。每项说明：

- 当前问题及证据路径；
- 建议改动和涉及范围；
- 预期收益、代价与回归风险；
- 是否与现行决策笔记冲突，以及推荐优先级。

没有值得做的重构时直接说明。默认用简洁的 Markdown 或小图呈现；用户要求可分享的可视化报告时再制作独立文件。确定要实施的新结构后，按 docs/decision-notes.md 记录决定，并在获得实施任务时更新代码。
