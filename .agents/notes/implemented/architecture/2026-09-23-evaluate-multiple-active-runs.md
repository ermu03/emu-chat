# Agent Note: 评估有限并行的活跃 Run

Status: implemented

## Problem

原 TASK-7：[数据库唯一索引](../../../../migrations/0001_initial.sql) 使全局同时只有一个处于 `dispatching`、`accepted` 或 `reconciling` 状态的队列项。单用户本地工作台用串行调度换取简单的状态机和恢复流程；若两个会话都需要较长时间生成，后发起者必须等待。

## Decision

目前保持全局单活跃 Run，不增加并行槽位。2026-09-23 对本地开发库的 57 条已派发队列项（9 个会话）做只读统计：平均入队至首次派发等待 2.9 秒，最长 48.5 秒；3 条等待超过 30 秒，均与同会话已有 Run 重叠。没有任何队列项的等待区间与其他会话的活跃 Run 重叠。这个样本没有显示跨会话串行造成了实际等待。

Hermes 0.21.3 的 API Server 支持多 Run，并有可配置的并发上限（源码默认 10）；本地 Hermes 健康接口正常，但本次没有发起并行真实 Run。上游可能并行不等于本地值得立即并行。只有在实际使用中出现不可接受的跨会话等待时，再用同样的队列时间与 Run 时间交叉统计确认瓶颈，然后评估有限槽位数。

若以后实施，必须一起调整全局唯一索引、单行全局租约、[协调器](../../../../src/server/coordinator/admission-coordinator.ts)当前只检查一个活跃项的调度方式、队列恢复的全局活跃检查，以及重启对账和跨会话公平性。Hermes 达到自身上限时会返回 429；当前提交失败路径会拒绝队列项并暂停会话，不能直接把本地槽位数调大。

## Alternatives considered

- **有限并行槽位（原设想全局 2～3 个）**：可以缩短不同会话相互等待；当前样本没有这类等待，新增槽位需同时重做容量约束、租约和恢复流程，因此暂不实施，也不预设槽位数。
- **不设上限地跨会话并发**：等待最少；可能突破 Hermes 容量，也会放大租约与恢复竞态。
- **继续全局串行**：数据库约束直接、恢复边界清楚；长任务将来仍可能阻塞其他会话。当前证据支持保留。

## Consequences

保持当前派发和故障恢复边界，避免在未见收益时扩大核心消息链路的并发面。代价是未来若出现同时使用多个长会话，后发起的会话仍须等待；此时应重新测量跨会话等待，再决定是否实施。当前样本仅代表本地开发库，不能证明未来工作负载没有并行需求。
