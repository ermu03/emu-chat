# Agent Note: 修正长会话消息分页方向与偏移

Status: implemented

## Problem

[会话视图](../../../../src/client/state/use-conversation-view.ts)原先首次请求 `order: "oldest", limit: 100`，取得最早的 100 条，顶部「加载更早历史消息」却继续以 `oldest` 和当前消息数量作为 offset，实际取得的是后续页。Run 终态对账会合并最新 100 条；合并后数组长度不再是连续历史页的偏移量，可能跳过中间消息。[先前的分页与对账决定](2026-09-23-keep-long-conversation-messages-visible.md)解决了最新回答在终态后消失的问题，但没有保证完整历史可连续加载。

## Decision

- 首次打开会话显式请求 `order: "latest"` 的最新 100 条，展示时仍按消息 ID 升序排列。
- 用最早已加载消息的 ID 和它在最近一次 Hermes `latest` 结果中的 offset 作为独立历史游标，并随会话视图快照缓存。加载更早历史时从该位置请求下一页，找到 ID 更小的消息后才推进游标；不再用合并后数组长度计算 offset。
- 新消息会把 `latest` 排序中的旧游标位置向后推移。历史翻页按页重叠一个消息继续扫描，直到找到比游标 ID 更早的消息。Run 终态对账和缓存会话刷新则从最新页向旧扫描，直到触及已知的最新消息，补齐超过一页的新消息；合并仍按 ID 去重。

## Alternatives considered

- 保持 `oldest` 初始加载并将按钮改名为「加载更多」：改动较小，但长会话首次进入仍看不到最新上下文。
- 每次取得完整消息历史：逻辑简单，但长会话的网络与渲染成本会持续增长。

## Consequences

- 首次进入长会话能看到最新消息；终态新增超过一页消息、翻页期间新增消息，以及切换会话恢复缓存后，仍能向上连续加载旧消息。
- offset 只有位置而非稳定游标；新消息插入时可能产生重复请求。实现依赖 Hermes 的 `latest` 结果按 ID 降序、消息 ID 随时间递增，并用 ID 重叠和去重恢复连续性。如果上游提供稳定的游标分页，可改用上游游标减少扫描请求。

## Verification

`tests/components/app-shell-flow.test.tsx` 覆盖 260 条初始历史、终态新增 125 条、翻页期间再新增 10 条，以及切换会话后继续翻页；最终检查 395 条消息无遗漏、无重复。
