# Agent Note: 会话列表完整性与安全清理

Status: implemented

## Problem

2026-10-05 使用内存 SQLite 和模拟上游复现了旧查询误删：`listConversations` 等待旧 session 的详情期间，`getMessages` 已将同一会话采用为新 session；旧详情返回 404 后，本地会话与未发送草稿仍被删除。

原 [ConversationService](../../../../src/server/services/conversation-service.ts) 用查询前的会话快照调用 `removeMissingLocalConversation`；[ConversationRepository](../../../../src/server/db/repositories/conversation.repository.ts) 的删除只匹配会话 ID，没有复核查询时的 session 映射。删除还级联清理队列、Run、图片控制记录，并产生图片 scope 删除任务，因此列表刷新中的旧响应具有数据丢失风险。

原列表链路还存在完整性与读取成本问题：[AppShell](../../../../src/client/app.tsx) 只请求前 50 条并忽略 `has_more`，后端则在分页前串行查询所有注册会话。隔离数据包含 51 个会话时，首屏没有较旧的置顶会话，读取第一页仍调用上游 51 次；客户端没有取得该会话的后续页入口。补分页时必须同时考虑删除导致的边界移动及重复全扫描的成本。

## Decision

1. 自动清理通过仓储的预期 session 参数，在同一个 SQLite 即时事务中复核映射与 `delete_state=none`，执行条件删除。已有图片分支保护仍适用；只有实际删除才移除会话租约、写入图片 scope 删除任务及清理 SSE。outbox 失败时整个事务回滚。显式删除保持自己的 pending/failed 生命周期；受保护记录即使上游 404，也保留本地摘要和删除入口。
2. 列表和详情查询返回后复核本地映射；映射变化时最多重读一次，持续变化时列表跳过至下轮、详情返回冲突。最后更新时间也按预期映射写入，不将旧详情拼到新 session 上。
3. 分页从本地注册表按 `custom_order ASC, created_at DESC, id ASC` 取 limit+1 条，仅为当前页读取上游详情，并发上限 4。私有接口改用保存本地排序位置的不透明游标；游标按最后检查记录推进，空页和已删除边界仍能继续，不重新全量读取上游。增量迁移只添加排序索引，不改写既有迁移或记录。所有读取均受本地注册表约束，维持[会话所有权边界](../../../../docs/01-architecture.md)。
4. 客户端每轮持续遍历全部页、按 ID 合并。分页回写核对轮次代数；渐进加载保留尚未刷新到的旧条目，完成后替换为整轮结果。保留置顶分组与本地排序，使较旧置顶会话可达。
5. 同步[服务端说明](../../../../docs/04-server-internals.md)、[客户端说明](../../../../docs/06-client-internals.md)和[接口文档](../../../../docs/08-api-reference.md)。自动清理与[图片引用保护](../../proposed/bug-fix/2026-10-05-preserve-media-references-through-branch-and-delete.md)沿用“确认删除后才释放资源”的边界。

## Alternatives considered

- **只在删除前再读一次映射**：改动少，能发现部分旧响应。但读取与删除之间仍可能发生映射变更，需要将复核与条件删除放在同一事务内。
- **保留后端全扫描，仅让客户端读取全部页面**：能快速恢复 50 条以后的会话入口，也保留当前按上游有效结果分页的方式。但每页重复查询全部注册会话，分页越多成本越高，清理与 offset 移动也仍需一起处理。
- **增加长期元数据缓存或优先接入上游批量接口**：可能进一步减少网络往返。但需要验证批量接口、缓存失效及所有权过滤；先实现按需分页和有界读取，额外缓存或批量能力作为实际查询成本仍过高时的候选。

## Consequences

- 旧详情返回 404 时，已采用新 session 的会话、未发送草稿、队列、Run 和图片引用保持完整；当前映射确实失效时，清理及副作用幂等。
- 静态列表超过 50 条仍完整遍历，后续页不重复读取已检查范围的元数据。缺失项减少一页条数，但游标仍推进，避免因清理跳过剩余会话。
- 有界并发与单次重读限制上游负载；客户端仍需要读取所有注册会话才能形成完整侧栏，没有加入长期元数据缓存。
- 游标不是数据库快照。会话顺序或集合在翻页中变化时，可能需要从首项重读；本客户端的会话修改成功后触发重载，ID 去重与代数隔离防止重复和旧轮次覆盖。其他进程改变排序需下一轮重载。
- 受显式删除或图片分支保护的缺失项使用本地摘要，不能提供上游标题、置顶或消息计数；这些占位字段不缓存，也不自动导入其他会话。

## Verification

- 仓储并发测试核对旧映射、pending/failed 状态拒绝清理，以及 outbox 失败时草稿与租约共同回滚。
- 核心读取与恢复测试挂起旧详情，实际调用消息读取采用新 session，再返回旧 404；核对保留草稿、队列、Run、图片控制记录及没有 scope 删除任务。旧成功详情也按新映射重读；真实缺失清理只产生一次 SSE/outbox 副作用。
- 53 条注册会话中清理第一页首项及游标末项，剩余记录与较旧置顶仍可遍历；三页分别读取 50、2、1 次，覆盖 null 排序前缀及同一非空 custom_order 内推进，最大并发为 4。
- AppShell 异步交互测试让旧分页请求悬挂，修改标题启动新轮次；验证 50 条以后的置顶会话可选择、跨页重复 ID 合并、旧页不能回写新列表。

- 完整 `npm test`：19 个文件、105 个用例通过；`npm run typecheck`、`npm run lint`、`npm run format:check` 与 `npm run build` 通过。最终补充 custom_order 分组推进后，相关 4 个场景重跑通过。构建仍有已有的大 bundle 提示。
