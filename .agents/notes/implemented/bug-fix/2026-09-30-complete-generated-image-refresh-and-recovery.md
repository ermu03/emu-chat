# Agent Note: 补齐生图保存完成刷新与分块 JSON 恢复

Status: implemented

## Problem

2026-09-30 发版前检查以 emu-chat `650e923` 和独立插件 hermes-emu-media `fbd7ec7` 为基线，发现两处可复现缺陷。关联已有[图片工作流决定](../feature/2026-09-28-add-image-workflows.md)。

1. **Run 结束后，异步保存完成不会刷新图片。** `src/client/state/use-run-runtime.ts` 只在 Run 活跃、终态同步或队列活跃时轮询；插件采集 worker 的完成时间可以晚于这些状态。隔离 AppShell 复现中，历史首次返回 pending 图片，随后模拟后端变成 ready；四秒后历史请求仍只有一次，页面继续显示“图片保存中”。`src/client/features/media/media-assets.tsx` 的保存重试也没有触发后续历史更新。漏 Hook 的历史补偿还可能在首次装饰历史之后才创建采集任务，不能仅依赖已有 pending 附件决定是否刷新。
2. **插件将一次网络读取误当作完整 JSON。** 插件仓库 `emu_media/reconcile.py::_history_page` 和 `emu_media/api.py::_json` 使用 `StreamReader.read(limit + 1)` 后立即解析。该调用可以只返回当前到达的部分字节。临时本机 aiohttp 服务将合法历史 JSON 分两块返回，复现 `history_unavailable`；合法私有 API JSON 请求分两块发送，复现 HTTP 422 `invalid_json`。因此历史补偿和正常私有接口都可能因传输分块失败。

## Decision

- 当前 Run 已结束、含成功的 `image_generate` 工具块且结果缺失或仍为 pending 时，前端每 2.5 秒刷新当前会话历史，最多 90 秒。刷新复用 `ViewTarget`，切换会话会清理定时器并忽略旧目标响应。资源进入就绪或其他终态后自动停止。
- 用户重试已知的采集失败资源后，图片卡片每 2.5 秒查询该工具调用的资产列表，最多 90 秒；服务端同步到新状态后卡片直接展示新资源。重试只再次采集，不调用模型。
- 插件新增 `read_limited`，在字节总量限制内循环读到 EOF 后解析 Hermes 历史和插件 JSON 请求；超限仍最多读取限制外一个字节，保留 15 秒请求超时及历史客户端超时。

## Alternatives considered

- **由 Hermes 推送图片就绪事件。** 能及时更新并减少轮询，但采集属于独立插件，不是 Hermes Run 生命周期事件；需要额外事件通道和重连恢复。当前优先考虑在已有私有历史接口上补齐有界刷新，保留独立插件约束。
- **将网络响应完整读入后再检查大小。** 代码简单，也能避免提前解析；但会失去读取期间的内存上限。采用循环累计并在超过上限时终止。

## Consequences

- 采集 Hook 晚到或历史补偿先于资产保存时，当前会话能自动呈现最终资源；网络/API 错误不会留下无期限轮询。90 秒后若资源仍未就绪，用户可以手动刷新或再次重试。
- 消息刷新可能在最多 90 秒内每 2.5 秒触发一次历史补偿请求；插件服务端对同一会话合并并发 reconcile。重试卡片只查询其工具调用的资产列表。
- 网络响应仍有界缓冲；超过限制时最多额外读取一个字节用于拒绝。

## Risks

- 新增刷新会增加历史查询和补偿请求，需要避免重复对账、无期限轮询和跨会话竞态。
- 网络读取修复必须同时保持总量上限和超时，不能以修复截断为由无限制缓存请求或响应。
- 以上检查不证明第三方供应商所有参数和图片编辑均兼容；发布前若承诺编辑可用，仍需用户授权的真实供应商编辑验证。
