# Agent Note: 评估有限并行的活跃 Run

Status: proposed

## Problem

原 TASK-7：[数据库唯一索引](../../../../migrations/0001_initial.sql) 使全局同时只有一个处于 `dispatching`、`accepted` 或 `reconciling` 状态的队列项。单用户本地工作台目前用串行调度换取简单的状态机和恢复流程；若两个会话都需要较长时间生成，后发起者必须等待。

## Proposal

只有实际使用表明跨会话等待不可接受时，再评估有限并行槽位（原设想为全局 2～3 个），同时保留每会话单活跃 Run 的约束。设计时一并处理全局租约、协调器领取、公平性、进程重启恢复和 Hermes 的实际并发能力。未达到这个触发条件时保持现行串行策略。

## Alternatives considered

- **继续全局串行**：数据库约束直接、恢复边界清楚；长任务会阻塞其他会话。当前适合项目规模。
- **不设上限地跨会话并发**：等待最少；可能突破 Hermes 容量，也会放大租约与恢复竞态。
- **有限并行槽位**：在等待时间与协调复杂度之间折中，具体槽位数需测量而非预设。

## Acceptance criteria

若决定实施：不同会话可在配置上限内同时运行；同一会话仍互斥，超过上限的任务安全排队；重启和租约恢复不会重复派发。

## Risks

改动唯一索引和租约模型会触及核心消息链路；收益尚未通过实际使用数据确认，因此本提案当前不表示立即实施。
