# Agent Note: 收窄会话视图接口并集中异步写入校验

Status: proposed

## Problem

2026-09-26 对提交 `0b325d6` 的架构评估发现，[useConversationView](../../../../src/client/state/use-conversation-view.ts)虽然持有会话视图状态，但仍返回 `setActiveConversation`、`setMessages`、`setDraft` 及多个内部 ref，并以整个 Hook 的返回类型作为调用方接口。AppShell、发送和运行 Hook 因此需要各自判断异步响应是否仍适用于当前视图。

已复现的入口是 [AppShell.handleUpdateMetadata](../../../../src/client/app.tsx)：等待元数据保存和列表刷新后，它使用异步开始时捕获的 `activeConversationId` 与 `activeConversation` 判断是否更新视图，再直接调用 `view.setActiveConversation`。在 A 中开始重命名，延迟保存响应，切换至 B 并等待其输入框可编辑，然后释放 A 的响应；B 的消息仍显示，但会话详情被旧的 A 快照替换，输入框卸载并停留在“正在准备输入框…”状态。

该实验使用真实 AppShell、jsdom 和延迟 API 替身，在 Node.js 26.9.0 下完成，没有连接真实后端。已确认的是会话状态错配和输入框卸载，未在该实验中验证未保存输入是否丢失。[现有组件用例](../../../../tests/components/app-shell-flow.test.tsx)覆盖会话消息加载时的旧响应隔离，尚未覆盖重命名回调这条路径。

此外，会话加载与 [useRunRuntime](../../../../src/client/state/use-run-runtime.ts) 都读取并应用 Queue／Run 状态，使用的请求代数和更新入口并不完全一致。单独修复重命名可以消除当前症状，但暴露底层 setter 的接口仍要求每个新调用方记住同样的约束。

## Proposal

优先级：中；已复现的重命名故障可先局部修复，再逐步收窄接口。保留现有三个 Hook 的职责，将异步结果能否写入当前视图的判断集中在状态所有者内部。

1. 用明确的只读视图和业务更新方法替代整包返回类型以及跨模块的底层 setter、可写 ref。调用方只提交带目标会话 ID 的结果；需要读取最新运行上下文时，由视图提供受限的快照读取方法，不要求调用方维护 state 与 ref 的同步顺序。
2. 对依赖当前选择的异步任务，在开始时捕获会话 ID 与请求代数，提交结果时由视图统一验证。校验必须区分 A → B → A 的两次选择，不能只比较会话 ID。Run 更新同时检查 Run 身份和终态，避免消息加载、轮询或操作回调覆盖更新的数据。
3. 元数据变更按目标会话应用字段级更新，不写回异步开始时的整份会话快照。目标已经离开当前视图时，更新或失效对应缓存并刷新列表；后台操作的成功结果仍应能在回到目标会话时读取到。
4. 从 AppShell 的元数据更新入口开始，随后将发送、运行和会话加载的共享状态写入迁移到受约束的方法。`DraftComposer` 继续持有尚未保存的编辑内容及保存队列；运行 Hook 继续负责 SSE 和轮询。只有重复逻辑在迁移后仍存在时，再评估抽取共同的加载操作，不同时重写分页、消息渲染或缓存结构。

这落实并细化[三 Hook 与单一状态所有者的决定](../../implemented/architecture/2026-09-23-split-app-shell-responsibilities.md)，不取代[会话切换时保留视图的约定](../../implemented/bug-fix/2026-09-23-smooth-conversation-switching.md)或[流式与历史回复平稳交接的约定](../../implemented/feature/2026-09-24-progressive-tool-events-and-stable-run-handoff.md)。实施时同步更新[客户端内部实现](../../../../docs/06-client-internals.md)和[数据流](../../../../docs/07-data-flow.md)。

## Alternatives considered

- **只给重命名回调增加当前会话检查**：改动小，能快速修复已复现的问题；但其他调用方仍能直接写入内部状态，今后新增异步操作时容易重复犯错。适合作为第一步，后续仍应将检查移入业务更新入口。
- **立即把整个会话视图改成独立控制器或统一 reducer**：能集中表达加载、缓存和运行状态迁移；但一次迁移会触及草稿、分页与流式交接，当前证据尚不足以支持这么大的改动。先收窄现有 Hook 接口，再评估剩余复杂度。

## Acceptance criteria

- A 的重命名请求延迟返回期间切换到 B，返回后 B 的消息、会话详情与输入框仍一致，输入框保持可编辑；已有草稿和期间输入不会因旧回调卸载或覆盖而丢失。
- A → B → A 后，第一次选择 A 时启动的旧视图请求不能覆盖第二次选择的新状态；元数据确认只更新其对应字段，不回写旧的 Queue、Run 或草稿快照。
- 非当前会话的重命名或置顶成功后，列表和再次进入该会话的视图能显示最新值，同时不影响当前会话。
- AppShell、发送和运行 Hook 通过有目标上下文的业务方法更新共享状态，不能直接调用会话数据的底层 setter 或改写内部 ref；缓存恢复、分页补齐及流式到历史的交接继续工作。
- 在[现有跨模块组件测试](../../../../tests/components/app-shell-flow.test.tsx)中验证延迟元数据响应、切换及必要的编辑防丢失场景，复用已有草稿与运行链路用例。断言关注状态归属和可继续操作，不增加占位文字、图标等静态渲染测试。

## Risks

- 请求失效规则不能一概而论：当前视图加载、已提交的后台元数据变更、Run 事件和草稿保存各有身份与生命周期。若统一丢弃所有旧代数结果，可能让已成功保存的变更迟迟不在列表或缓存中出现。
- 元数据的字段级更新仍需处理同一字段多次修改的响应顺序；本轮只复现了跨会话回写，不能据此宣称所有并发编辑场景已经验证。
- 收窄接口可能导致调用方增加参数传递；应围绕实际操作提供少量方法，避免把原 setter 换名后继续暴露整份状态，或把防竞态逻辑重新分散回各个 Hook。
- 迁移期间必须保留输入框对未保存内容的所有权和旧保存响应保护。若需要同时重做缓存或分页才能推进，应先缩小改动范围，并在项目要求的 Node.js 22 环境完成关键交互验证。
