# Agent Note: 通过独立 Hermes 插件接入图片识别、生成与编辑

Status: proposed

## Problem

用户希望在 emu-chat 上传图片并识别内容，通过文字生成图片，以及对上传或生成的图片继续提出修改要求。重点是把上传、任务、结果保存和展示的基础设施做好；识图质量、生成效果、编辑效果和模型供应商由 Hermes 负责，不在 emu-chat 重做模型服务。

目前草稿、队列和 Run 提交只携带文字，历史消息也没有受管理的图片附件。工具返回的图片可能是短期 URL 或 Hermes 所在机器的文件路径，不能直接作为稳定的浏览器资源。工具实时事件只是进度提示，不能替代完整历史与图片索引。

用户已确认保持当前部署方式：emu-chat 从独立版本目录运行，Hermes 从官方 Git 安装目录运行；扩展以独立用户插件部署，不修改 Hermes 核心。官方更新后保留配置、会话及插件是目标，不要求单实例无停机升级。

本提案经项目 [grilling 技能](../../../skills/grilling/SKILL.md) 澄清。代码事实以 emu-chat `8ef8100`、本机已部署 Hermes `6005aa1` 为基线；开发目录里的 Hermes `f5d1926` 不是当前生产版本。源码阅读证明相关接口存在，不代表已经完成实际图片链路验证。

## Proposal

### 使用方式与首版边界

- 用户已确认：融入现有聊天，由提示词表达识别、生成或编辑意图，不增加三种模式切换和独立生图页面。
- 用户已确认：首版采用图片加文字指令，支持多轮继续编辑；不做蒙版、涂抹、框选区域或画布编辑器。
- 上传支持文件选择、粘贴和拖放；消息中的受管理图片支持查看大图、下载和“用于下一条消息”。选图只修改草稿，不自动提交或覆盖已有文字。
- 常规实现选择：一条消息最多附 4 张图片，上传首版支持静态 PNG、JPEG、WebP，每张上限 8 MiB；SVG 源码预览继续由[已有成果预览提案](2026-09-26-add-html-svg-artifact-preview.md)负责，不纳入图片编辑输入。多图能力不能超过当前上游实际支持范围，不允许静默丢弃参考图。
- 不建立图片任务的第二套执行队列。识图、生成、编辑继续使用现有会话、全局单活跃 Run、审批、停止和错误恢复流程。上传及生成结果入库是独立 I/O 状态，不占用新的模型执行槽位。
- 首版不做独立图库、公开分享链接、模型选择器、供应商管理、批量生成控制台，也不自动导入其他 Hermes 客户端的所有图片。

### 服务边界与数据归属

独立插件暂名 `emu-media`，开发仓库规划为 `/home/emu/projects/hermes-emu-media`，用户安装位置为 `$HERMES_HOME/plugins/emu-media`。本次只写提案，不创建插件仓库、不安装或启用插件。

插件通过官方 `register_platform_handler("api_server", factory)` 增加独立命名空间的资源接口，通过官方 Hook 接入图片工具输入和结果采集。继续使用 Hermes 原有 `vision_analyze`、`image_generate` 及其供应商配置；不得覆盖这些工具或复制供应商 SDK。插件自行持有图片文件、引用索引和未完成采集记录，不读写 Hermes 私有数据库，也不调用适配器私有方法。

emu-chat 后端代理图片上传、元数据及二进制读取，负责本地会话归属、附件草稿、队列快照和历史展示适配。浏览器仅访问 emu-chat 同源地址，不接触 Hermes 地址、文件路径、供应商临时 URL 或服务端凭据。新增图片模块不扩大 AppShell 或现有 HermesAdapter 的职责。

持久化分工：

- Hermes 继续持有权威聊天历史。
- 插件持有图片文件、附件提交标识、工具结果来源、会话引用、采集状态；不另存完整聊天副本。
- emu-chat 保存草稿与队列中的资源引用及必要的提交/清理控制记录，不将图片 Base64 塞入 SQLite 消息正文。
- 插件数据目录独立于插件代码，规划为 `$HERMES_HOME/emu-media/`。可重建的工具输入缓存与这份持久化目录分开。

用户已确认：图片随会话保留，最后一个引用删除后才清理。删除确认明确说明会清理本会话独占图片；仍被其他会话、分支、草稿或队列引用的图片保留。历史图片不设自动到期时间，不沿用队列 7 天保留期。未绑定成功的上传、被移除的未发送附件等无引用文件可延迟回收，具体边界见规格；不另建独立图库。

### 可靠性与发布约束

上传成功不等于草稿保存成功；图片工具执行成功也不等于图片已经保存。界面和存储必须区分这些状态。失败时允许重试上传、保存或下载，不能把“重试保存结果”变成再次调用付费图片工具。

附件必须与文字一起参与草稿 revision、队列编辑、幂等指纹、失败恢复、会话切换及发送成功后的清理。历史附件使用稳定身份关联，不能按相同文字、相近时间或工具名猜测归属。会话压缩换 ID、分支和删除都必须处理图片引用。

插件路由需要显式鉴权：当前 Hermes 的认证主要在原有 handler 中执行，不能假设挂到 aiohttp 路由后自动获得保护。具体协议、状态、边界、源码依据和开发工作包放在[实施规格](../../../specs/2026-09-28-image-workflows.md)。

当前 [AGENTS.md](../../../../AGENTS.md) 关于“尚未部署、可以丢弃开发数据”的说明已落后于实际部署及用户要求。本功能采用增量迁移保留已有数据，不修改已经应用的初始迁移来代替升级，不删除数据库。实施时同步纠正文档中的过时前提。本次不改业务代码、生产配置或部署方式。

### 开发拆分

分为六个可交接的工作包，依赖、交付物和验收条件见规格，不另建待办索引：

1. **P0：兼容性验证与接口定稿。** 在隔离环境验证实际 `/v1/runs`、Hook、工具输入和历史关联；先排除需要改 Hermes 核心才能实现的路径。
2. **P1：插件资源存储与接口。** 实现上传、稳定读取、引用管理、鉴权和持久化。
3. **P2：插件工具接入与结果采集。** 连接已上传图片与 Hermes 工具，持久化输出，处理漏事件、失败和重启。
4. **P3：emu-chat 后端附件链路。** 扩展草稿、队列、幂等、恢复、代理和历史关联。
5. **P4：前端图片交互。** 上传、附件草稿、历史图片、大图、下载和继续编辑。
6. **P5：联调、数据生命周期与发布验证。** 验证跨服务故障、会话分支/删除、增量迁移及升级后数据保留，补部署与维护文档。

P0 必须先完成；P1 之后 P2、P3 可按统一协议分别开发，P4 依赖后端契约，P5 验收整体。六块不等于六个独立部署服务，不要求六次生产发布。

## Alternatives considered

- **直接修改 Hermes API Server 和工具实现。** 可以直接拿到内部状态，路径最短；但增加官方升级时的合并和维护成本，用户已明确选择独立用户插件，因此不采用。
- **emu-chat 直接调用图片模型 API。** 可绕过 Hermes 工具输入与结果格式的适配；但会形成第二套模型配置、计费调用、任务和历史逻辑，与既定职责分工不符。
- **浏览器直接加载工具返回 URL 或读取服务器路径。** 实现简单，适合一次性展示；但有失效、路径不可达和凭据暴露问题，不能满足重启与刷新后持续读取。
- **直接把图片作为原生多模态内容提交。** 能让主模型直接看图，长期有价值；目前 emu-chat 的 Run 和历史契约是文字，生产 Hermes 的 `/v1/runs` 路径也不能仅凭其他 API 的多模态解析器判定完全兼容。首版以原有图片工具链路为基础，P0 验证具体桥接方式，不以切换 `/v1/responses` 绕开现有 Run 恢复能力。
- **独立图片工作台与可视化编辑器。** 可显式控制模型参数、区域和版本；用户选择先融入聊天，保留轻量界面。

## Acceptance criteria

- 输入生成要求后，通过 Hermes 图片工具执行，结果在会话中展示，可重复打开、下载；浏览器刷新和服务重启后仍可读取。
- 上传图片并提出识图或编辑要求后，实际输入图传递到相应 Hermes 工具；输入和结果都有明确来源。对结果点击“用于下一条消息”能继续编辑，旧结果不被覆盖。
- 文字与附件一起保存、排队、编辑和恢复；发送失败、迟到响应、切换会话或插件短暂不可用，不丢失已保存草稿、不串图、不无故重复执行图片工具。
- 工具输出已产生但保存失败时，显示独立的保存状态；重试采集不创建新 Run。漏 Hook 可从权威历史补偿，无法恢复的输出诚实标记不可用。
- 插件缺失或版本不兼容时，普通文字聊天仍可使用；图片功能给出明确状态，不使整个 Hermes 连接被误判为不可用。
- 会话压缩、分支、引用复用和删除遵循已确认的“最后一个引用删除后清理”策略；本地控制记录到期不破坏历史图片。
- 在受控测试环境完成插件重装、Hermes 重启/升级及 emu-chat 增量迁移验证，原有配置、会话、图片和插件数据保留，Hermes 核心工作区无定制补丁。
- 自动化集中于附件数据一致性、幂等、防丢失与跨服务恢复；真实浏览器验证上传、移动端、大图和下载，不增加静态按钮/文案测试。模型画面质量不作为基础设施验收标准。

## Risks

- 官方 Hook、工具结果格式和具体供应商输入能力存在版本差异；P0 是开工门槛，不能把源码存在接口写成端到端已经可用。
- Hook 是尽力通知，结果 URL 也可能过期；持久化待采集任务和历史补偿降低丢图概率，但不能追回从未留有可访问来源的图片。
- 没有模式切换意味着模型负责判断意图，不能保证每次自然语言都触发指定工具；说明和能力探测应准确，工具未调用时不能显示“图片已生成”。
- 跨服务引用与删除不能靠单个数据库事务完成，需要可重试的控制记录、延迟物理清理和重启对账。
- 图片增加磁盘、解码内存及带宽开销。达到容量限制时显式失败，不自动删除仍被引用的历史图片。
- 现有 emu-chat 是单用户应用，图片沿用其部署访问边界；同源代理不等于新增了用户登录或公网私密分享能力。
