# Agent Note: 统一清理队列中的完整正文副本

Status: proposed

## Problem

本篇安排在三项优先保护之后。2026-10-05 使用内存 SQLite 复现确认：图片队列到期或主动丢弃恢复载荷后，`payload_text` 已为空，`payload_run_input` 仍包含完整用户正文；待人工核对项模拟经过 100 天后仍保留该副本。

[MediaDispatchService](../../../../src/server/media/dispatch.ts) 冻结的 Run 输入由[清单构造器](../../../../src/server/media/manifest.ts)将原文与机器清单拼接形成。[QueueRepository](../../../../src/server/db/repositories/queue.repository.ts) 的终态迁移和到期清理，以及[QueueRunService](../../../../src/server/services/queue-run-service.ts) 的主动丢弃只清空 `payload_text`。`review_required` 控制记录按现有决定保留，导致冻结正文绕过恢复期限；普通终态也会在控制记录清除前多留一份正文。

清空冻结列还涉及历史关联：[MediaService.decorateHistory](../../../../src/server/media/service.ts) 当前把冻结输入与 Hermes 用户消息比较，作为本地图片清单验证依据。因此需要用不含完整正文的摘要和身份记录替代这一证明，保留插件离线时的历史关联能力，而不能仅增加一条清空 SQL。

本篇补全[恢复载荷保留决定](../../implemented/bug-fix/2026-09-23-expire-recovery-and-terminal-control.md)在图片输入上的边界。Hermes 仍是完整历史的权威存储；图片引用保护见[关联提案](2026-10-05-preserve-media-references-through-branch-and-delete.md)。

## Proposal

1. 在已有正文生命周期规则下统一清理所有完整正文副本：完成或取消时清空，到期恢复项由有界后台批次清空，主动丢弃在同一事务中清空。接口仍在截止时间立即停止提供恢复内容，`review_required` 的控制身份可以继续保留。
2. 把 scope、operation、冻结 session、有序附件身份、用户文字摘要和冻结输入摘要作为不含正文的验证凭据保留。历史清单与这些身份和摘要逐项匹配后才装饰图片；未知或不匹配的清单继续按现有保守验证处理。
3. 新请求在冻结输入阶段记录验证凭据。旧记录在清空前用仍存在的冻结输入建立可验证凭据；缺少本地证明时按插件绑定核对，不能猜测摘要或放宽权限。若需要新增持久字段或凭据表，使用增量迁移，保护部署数据并保持升级过程可恢复。
4. 在现有保留服务内补清 `payload_text` 已为空、冻结列仍有正文的旧终态、已丢弃及已到期记录；批次有界且重启可继续。仍处于提交、接纳或对账执行阶段的输入保持可用，幂等重放仍使用原 session、正文、附件顺序与键。
5. 正文清理与图片引用释放分别遵循各自规则。保留必要的历史关联和引用交接凭据，清空正文不等于丢弃历史图片。实现时同步[数据模型](../../../../docs/02-data-model.md)、[正文状态机](../../../../docs/03-state-machines.md)、[图片集成说明](../../../../docs/05-hermes-integration.md)及相关决定的后续边界。

## Alternatives considered

- **只清空 `payload_run_input`**：可直接减少敏感正文留存，改动较小。但历史目前依赖该列做本地验证，直接清空会让插件离线时已知输入图片失去证明，需要一起保留摘要与身份信息。
- **等待整个控制记录到期再删除正文**：可复用既有控制清理，并保留历史校验依据。但控制记录与正文保留期限不同，待人工核对项还可能长期保留，不能满足主动丢弃和七天恢复约定。
- **清空后完全依赖插件在线校验**：能少存一份本地验证凭据。但会增加历史读取的远端请求，并在插件暂时不可用时退化已知附件展示，选择保留受验证的摘要凭据。

## Acceptance criteria

- 新图片队列完成、取消、到期或主动丢弃后，相关本地逻辑字段不再含完整用户正文，API 恢复可用性与清理状态一致。
- 升级前已完成、已丢弃或已到期记录的冻结正文由有界批次补清；`review_required` 即使长期保留控制记录，也不会长期保留已过期或已丢弃正文。
- 正常提交、丢失接纳响应后重放及重启恢复仍使用完全相同的冻结请求，不被补清批次误伤。
- 清理后，已验证的历史输入图在插件在线及离线时仍保留正确关联；摘要、scope、session、operation 或附件顺序不匹配的清单不能通过验证。
- 历史图片、有效恢复附件和待交接引用不随正文清空而丢失；新摘要记录的存续与控制及图片关联需要一致。
- 在[保留策略测试](../../../../tests/unit/data-retention.test.ts)、[图片主干集成测试](../../../../tests/integration/media-run-flow.test.ts)及既有重放恢复测试中验证新旧记录清理、活跃保护和历史关联，按[AGENTS.md](../../../../AGENTS.md)维护必要测试。

## Risks

- 清理阶段判断错误会破坏幂等重放；所有后台补清必须复核当前队列与 Run 状态，不能仅凭字段为空推断可清理。
- 摘要凭据需要明确来源与信任边界。由用户消息现算出的摘要不能独立充当授权依据，应与已经冻结或由插件核验的凭据比较。
- 旧记录的摘要补建与清空顺序需要可恢复。缺少验证依据时，历史展示维持待核对状态，不能为了剥离清单而放宽验证。
- 本篇验收针对逻辑记录和 API 的正文保留。SQLite 空闲页、WAL 和已有备份的物理擦除不由置空字段保证；文件空间整理仍沿用[按实际占用回收的决定](../../implemented/architecture/2026-09-23-reclaim-sqlite-free-pages.md)。
