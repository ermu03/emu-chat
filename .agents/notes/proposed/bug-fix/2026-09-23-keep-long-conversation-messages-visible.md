# Agent Note: 长对话消息分页与终态对账

Status: proposed

## Problem

原 BUG-1 与 ISSUE-6 是同一条消息分页链路的问题。[AppShell](../../../../src/client/app.tsx) 初次加载和 Run 终态对账都只请求最早的 100 条消息；对账时又用这页数据替换消息列表并清除流式内容。会话超过 100 条后，新回答可能已写入 Hermes，却从界面消失。

[HermesAdapter](../../../../src/server/hermes/adapter.ts) 把 `has_more` 固定为 `false`，把本页条数当成 `total`；[共享响应 Schema](../../../../src/shared/api-schemas.ts) 则没有这两个字段。现有 Hermes 响应样本的 `pagination` 可能为空，不能假定上游总会提供总数。原 BUG-1 提到的流式卡顿另见[会话切换与消息渲染提案](2026-09-23-smooth-conversation-switching.md)。

## Proposal

先确认 Hermes 在 `oldest`、`latest` 两种顺序下的分页语义和可用元数据，再定义可靠的前后端分页契约。客户端打开长会话时应能看到最新消息，也能按需获取更早消息；Run 对账后须先让持久化的新回答可见，再结束对应的流式展示。分页合并时按消息 ID 去重并维持显示顺序。

若上游没有总数或 `has_more`，就用实际页大小、后续请求或明确的“未知”语义处理，不能继续报告虚假的 `total` / `has_more`。

## Alternatives considered

- **每次拉完全部历史**：实现直观，也容易避免缺页；长对话会带来更多请求与渲染成本。
- **只用 `offset: messages.length` 增量追加**：对账请求较小；消息过滤、重试、会话切换或上游顺序变化时，偏移量可能不等于已展示条数，需先验证。
- **先加载最新一页，再按需补旧页**：优先保证新回答可见；需要处理逆序分页、去重和滚动位置。当前倾向此方向，具体算法待核实 Hermes 契约后确定。

## Acceptance criteria

- 超过 120 条消息的会话在打开、流式生成结束和再次进入后，最新回答都保持可见。
- 更早消息仍可获取；多页拼接不重不漏，顺序稳定。
- 对账请求失败时，不把尚未确认持久化的回答无声清空；分页元数据不报告已知错误的结果。

## Risks

不同分页顺序和会话追加消息可能造成页边界漂移；需要用真实 Hermes 响应核对，再决定客户端合并策略。
