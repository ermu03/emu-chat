# Agent Note: 上游 SSE 断线恢复与连接释放

Status: proposed

## Problem

本篇后置实施，先核实上游事件契约。2026-10-05 的模拟上游复现确认：[AdmissionCoordinator.consume](../../../../src/server/coordinator/admission-coordinator.ts) 遇到断线后结束消费，后续 `recoverRun` 只轮询状态。同一 Run 仍为 `running`，经过四次状态查询，事件订阅次数仍为 1，后续文字与工具事件没有新的消费入口。启动恢复已接纳 Run 的路径同样只进入状态对账。

此外，[HermesClient.stream](../../../../src/server/hermes/client.ts) 的 `finally` 只清除握手计时器。隔离 ReadableStream 中，调用生成器 `return` 后，取消读取次数为 0、请求未中止、响应流仍被锁定。消费者提前结束或协议解析失败时可能留下读取及连接资源。

[HermesAdapter](../../../../src/server/hermes/adapter.ts) 可以透传上游帧的 `id`，但当前消费未使用它。尚未核实真实部署对事件 ID、指定游标续订、重放范围及进程重启的保证。本地 `local_seq` 只代表转发顺序，不能当作上游去重或恢复游标。本次已证明订阅与资源管理缺口，完整真实上游重连行为仍待验证。

## Proposal

1. 先通过当前 Hermes 的公开协议与隔离验证确认：事件身份是否稳定、重新订阅会返回哪些旧事件、能否带游标继续、正常结束和临时断线如何区分。把结果和支持边界记入[Hermes 集成说明](../../../../docs/05-hermes-integration.md)，据此选择续订与去重方式。
2. 由协调器集中持有每个现有 Run 的事件消费者、取消信号和重试状态。Run 仍活跃且当前实例持有有效租约时，初次接纳、断线后恢复和进程启动恢复均可建立消费；单 Run 同时至多一个有效消费者，断线退避有界，永久鉴权或协议错误保留可理解的缺口及对账状态。
3. 续订仍指向原 `hermes_run_id`。按已验证的上游身份或游标处理重放，避免把重复文字增量当成新事件叠加。无法恢复的过程保留 `stream.gap` 与权威历史核对，继续由 REST 轮询推进终态。若公开契约不足以安全处理重放，明确记录所需契约与回退方式，不能以新本地序号伪造去重保证。
4. 将取消能力贯通协调器、适配器和 HTTP 客户端。正常结束、提前退出、解析失败、租约丢失和服务停止都能终止底层请求、取消读取并释放锁；取消后的异常与回调按当前生命周期识别，不能重新启动旧消费者。
5. 沿用[集中 Run 生命周期的决定](../../implemented/architecture/2026-09-26-centralize-run-lifecycle-and-recovery.md)中的事务、租约与旧回调保护，以及[实时到历史交接](../../implemented/feature/2026-09-24-progressive-tool-events-and-stable-run-handoff.md)的内容保护。实现时同步[实时数据流](../../../../docs/07-data-flow.md)与服务端说明；暂停与真正进入终态的区别参见[停止暂停决定](../../implemented/bug-fix/2026-10-03-paused-queue-false-generating.md)。

## Alternatives considered

- **继续仅轮询 Run 状态**：能用权威状态推进终态，避免复杂重放，是可靠的兜底。但一次临时断线会让余下整个 Run 的文字和工具过程失去实时反馈，选择在此兜底之上恢复事件消费。
- **断线后直接反复重开 SSE**：可以较快恢复新事件，代码入口也较少。但未验证上游回放范围时会重复叠加文字，旧连接未退出还可能产生并行消费者，需要先明确身份、去重及资源收尾。
- **新增本地持久事件副本**：能扩大浏览器回放窗口，但无法替代上游断线期间的取回契约，也扩大存储和保留策略；当前继续使用有界内存窗口、缺口提示与权威历史。

## Acceptance criteria

- 上游续订与重放语义有可复查的一手协议或隔离验证依据，明确支持的恢复边界及不能恢复的过程。
- 已接纳 Run 临时断线后，能够继续转发同一 Run 的新文字和工具事件；过程缺口仍可见，重复事件不会重复展示。
- 进程启动恢复活跃 Run 时重新建立允许的事件消费和状态对账；整个恢复过程不会调用 `startRun` 创建第二次执行。
- 重复唤醒、状态轮询和重连交错时，单 Run 至多一个有效消费者；租约换主后，旧回调不能写入或重启消费。
- 上游终态、消费者提前结束、协议错误及服务停止后，底层读取和连接被释放，计时器与重试结束。用户请求停止但上游尚未终止时，仍保留可靠的终态确认路径。
- 终态历史延迟时保留已展示内容及展开状态；最终以 Hermes 历史核对结果。永久连接错误不造成无限快速重试或阻塞其他会话。
- 在[HTTP/SSE 客户端测试](../../../../tests/unit/hermes-client.test.ts)、[Run 状态并发测试](../../../../tests/unit/run-lifecycle.test.ts)与核心恢复集成中补必要的断线、重放和资源释放场景，按[AGENTS.md](../../../../AGENTS.md)选择验证范围。

## Risks

- 上游事件 ID 可能缺失或不支持游标重放，需先验证，不能承诺恢复全部历史过程。公开契约缺口需要另行记录实际依据与取舍。
- 后续文字增量不是完整快照，重复转发会污染当前显示；仅凭事件内容相同或时间相近去重还可能丢掉合法重复内容。
- 取消、终态和重连同时发生时，需要防止旧消费者重新入场；网络结束也不能被错误解释为 Run 已完成。
- 请求停止与上游进入终态是两个阶段。连接收尾要与租约及统一对账配合，不能仅凭队列暂停就丢弃停止确认或已有内容。
- 本篇限于连接生命周期与既有 Run 恢复。SSE 环形缓冲序列化优化和前端主包拆分继续暂缓。
