# 实施计划与验收测试

状态：MVP 已批准实施计划
更新时间：2026-09-19

## 1. 技术基线

- 单仓库、单 `package.json`、TypeScript；
- React + Vite 客户端；
- Fastify 长驻 Node 后端，生产时同一进程提供静态前端和 `/api/v1`；
- SQLite + `better-sqlite3`，显式 SQL migration/repository；
- REST/JSON + SSE；
- Zod 作为共享边界 schema；
- Zustand 只管理客户端 UI/临时流，不持久化 transcript；
- Markdown 使用 react-markdown/remark/rehype/KaTeX/sanitizer；
- 不使用 Next.js、Python 服务、ORM schema generator、GraphQL、WebSocket、serverless 或 Edge runtime。

精确目录、依赖 major、DDL、路由和枚举见 `11-Gemini编码交接基线.md`。

## 2. Gemini 编码权限

Gemini 只能在 `/home/emu/projects/emu-chat` 中创建/修改源文件和开发文档。明确禁止：

- 运行 `pnpm/npm/yarn install` 或修改全局环境；
- 启动 Vite/Fastify/Hermes/Docker；
- 运行 build、lint、format、typecheck、unit/integration/e2e test、coverage 或 smoke；

- 手工伪造 lockfile 或声称代码已经验证。

允许编写测试文件、fake Hermes server、fixture 和脚本，但只静态交付。每次交付必须列出：已写文件、仍未运行的命令、基于静态检查发现的限制。

## 3. 分阶段编码顺序

Gemini 必须按顺序完成；每阶段先阅读所有批准文档，不跨阶段自行扩范围。

### Phase 0：仓库骨架与共享契约

创建：

- `package.json`、`tsconfig*.json`、Vite/Fastify 配置、`.env.example`；
- `src/shared` 的 ID、枚举、Zod request/response/error/SSE schema；
- `src/server/config`、安全日志 redaction、统一错误类；
- `src/client` 应用壳和 typed API client；
- migration runner 与 `migrations/0001_initial.sql`；
- 根据 `09` 生成 `openapi/emu-chat-v1.yaml`，不得新增路由。

静态完成条件：目录和 import 方向符合 `11`；所有枚举只有批准值；无 archive、Session-Key 或 transcript table。

### Phase 1：SQLite repository 与状态机

实现：

- migration、PRAGMA、transaction helper；
- conversations/drafts/queue/runs/leases/preferences repositories；
- draft CAS、FIFO 分配、partial unique index 冲突映射；
- queue/run 纯状态 transition guards；
- 恢复正文 7 天清理逻辑；
- coordinator lease acquire/heartbeat/release/fencing。

同时编写但不运行 unit tests，覆盖合法/非法 transition、全局并发 1、FIFO、draft revision 和 payload cleanup。

### Phase 2：Hermes adapter 与只读会话

实现：

- server-only Bearer client、超时、capabilities/status；
- session list/detail/messages、exact ID/title search；
- effective session id 更新；
- create/title/pinned/fork/delete adapter 方法；
- 所有上游 response Zod safe-parse 和错误映射；
- fake Hermes fixtures（不启动）。

UI 先完成连接状态、会话列表、当前 segment 提示和消息安全渲染。不得实现全文搜索、archive 或 parent 拼接。

### Phase 3：草稿、队列和 coordinator

实现：

- draft API/自动保存/revision 冲突；
- atomic draft-to-queue send；
- global + conversation lease 和 FIFO dispatch；
- admission idempotency、最多 4 次总尝试、86400 秒 deadline；
- 离线发送拒绝且不清草稿；
- queue edit/cancel/resume；
- 启动恢复扫描。

同时编写但不运行 fake adapter tests，覆盖双标签发送、超时 replay、409 fingerprint、deadline 超时和重启扫描。

### Phase 4：Run、SSE、stop、approval 与对账

实现：

- run submit/status、唯一上游 events consumer；
- in-memory ring buffer、浏览器 fan-out、heartbeat、`stream.gap`；
- stop；
- approval `once|deny`；
- terminal -> status/messages reconciliation；
- non-success pause、人工复核和 7 天恢复副本；
- copy-to-draft/discard recovery；
- completed 后清正文与自动推进下一项。

不得实现 steer、session/always approval、事件持久表或已有 run id 的 retry endpoint。

### Phase 5：完整 UI 与生命周期

实现：

- 桌面侧栏、手机抽屉、消息区、运行栏、队列面板、输入区；
- 所有加载/空/失败/降级/离线/人工复核状态；
- new/reset/fork/title/pinned；
- 删除确认、expected session id、active 门禁和 pending/failed；
- LAN HTTP 警告与 PWA secure-context 降级；
- keyboard/focus/touch 基础可用性。

菜单不得出现 archive/restore/hide、附件、通知、语音、steer 或 OpenAI-compatible 设置。

### Phase 6：静态测试资产与交付说明

补全但不运行：

- unit tests；
- fake Hermes integration tests；
- React component tests；
- Playwright 场景文件；
- fixtures：XSS、长 Markdown、events gap、approval、session rollover、delete 404；
- `README` 的人工安装/运行/验证步骤。

不要创建测试通过截图、coverage、录制或运行结果。

## 4. 后续验证矩阵（由人工/独立验证阶段执行）

本节不是 Gemini 当前执行权限。

### 4.1 单元测试

- 所有 queue/run transition 与非法跳转；
- draft revision CAS；
- FIFO 和两个 partial unique index；
- lease fencing/过期接管；
- idempotency deadline、重试次数和 key/body/session 不变式；
- recovery expiry/copy/discard；
- upstream schema 与安全错误映射；
- sanitizer、URL、KaTeX、streaming fragment。

### 4.2 Fake Hermes 集成测试

至少覆盖：

1. list/detail/messages 正常、空和错误；
2. effective session id 轮换；
3. run 202、same-key replay、fingerprint 409；
4. 202 前后各崩溃窗口；
5. events 无 replay、断流、未知事件、非法 JSON；
6. stop 延迟终态；
7. approval once/deny、过期 request；
8. completed/failed+partial/cancelled/interrupted；
9. status 404 和 messages 对账超过 5 分钟；
10. delete 2xx、超时、404 二次确认、active_agents 门禁；
11. Hermes offline 时 draft 可保存但 send 不创建 queue；
12. 两标签页/两请求同时 dispatch 只有一个成功。

### 4.3 真实 Hermes 联调（未来人工执行）

- 先只读验证 health/capabilities/list/detail/messages；
- 使用专用测试 session，再验证 create/title/pinned/fork/delete；
- 真实模型 run、tool、approval、stop 必须由用户明确发起并记录成本；
- 不修改当前 Hermes 源码，不对生产历史做破坏性 fixture。

### 4.4 浏览器验收（未来人工执行）

- 手机 LAN HTTP、320/768/1280；
- HTTP 下无 Service Worker 时正常降级；
- 刷新、SSE 断开、后端重启；
- 两个标签页同时保存草稿/发送/stop/approval；
- XSS、危险链接、长 Markdown/LaTeX/代码；
- recovery copy 警告和 7 天到期；
- 删除真实影响文案；
- 前端/日志无 Hermes key、输入正文、内部路径。

## 5. 后续 Definition of Done

一项功能在未来验证阶段只有同时满足以下条件才算完成：

- 对应 `01` 中的需求 ID；
- 路由/schema/状态转移与 `09`/`11` 一致；
- 成功、失败、超时、刷新和竞态均有 fixture；
- 未新增 transcript/event 历史副本；
- 日志与错误脱敏；
- migration、实现、测试代码和用户文档同步；
- 由获准执行测试的人记录实际运行命令和结果。

Gemini 的“代码写完”不等于 Definition of Done，只等于“等待安装依赖和验证”。

## 6. Gemini 每阶段交付模板

交付信息固定包含：

1. 完成了哪些 phase/需求 ID；
2. 创建/修改的文件；

4. 明确声明“未安装依赖、未启动服务、未运行任何测试/构建/联调”；
5. 静态可见的未决问题（只能是实现 bug/文档冲突，不得擅自新增产品决策）；
6. 建议由人工运行的下一组命令，但不得代为执行。
