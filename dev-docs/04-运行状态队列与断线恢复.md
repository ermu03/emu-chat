# 运行状态、消息队列与断线恢复

状态：MVP 已批准实现基线
更新时间：2026-09-19

## 1. 固定并发与所有权

- MVP 全局最多一个 `dispatching|accepted|reconciling` queue item。
- 每个 conversation 最多一个上述 active item。
- 后端 coordinator 拥有 dispatch；浏览器标签页永远不是 lease owner。
- 每条用户输入是独立 operation/run，禁止把多个队列项合并到一个 Hermes input。
- 这些约束只覆盖经 emu-chat 提交的 run；其他 Hermes 客户端仍可能并发写，UI 不宣称跨客户端原子串行。

## 2. 草稿不是队列

```text
draft（每会话 0 或 1）
  ├─保存/编辑→ draft
  ├─Hermes 非 healthy→ 只能保留 draft
  └─用户明确发送 + 健康/版本/状态校验通过
       → 事务创建 queued item、清空 draft content 并 revision + 1
```

- 草稿没有自动发送能力，不占 FIFO，不持有 idempotency key。
- 连接从离线变健康时不执行任何草稿操作。
- 多标签页通过 `revision` CAS 更新；冲突时保留服务器版本并提示重新合并，不做 last-write-wins 静默覆盖。

## 3. Queue item 状态机

批准枚举：

```text
queued
  ├─编辑→ queued（revision + 1）
  ├─用户取消→ cancelled（立即清正文）
  └─取得 global + conversation lease→ dispatching

dispatching（无 run_id）
  ├─Hermes 202→ accepted（写入 run_id，保留正文）
  ├─明确 non-retryable 4xx 且确定未接纳→ rejected（暂停队列，正文保留 7 天）
  ├─409 幂等 fingerprint 冲突→ review_required
  ├─网络/429/5xx 且仍在 admission deadline→ 同 key/body/session 有界恢复
  └─期限已过或无法安全判断→ review_required（暂停，正文保留 7 天）

accepted（已有 run_id）
  ├─仍为非终态→ accepted
  └─读到终态→ reconciling

reconciling
  ├─completed + messages 成功→ done（清正文，可自动推进）
  ├─failed/cancelled/interrupted + messages 成功→ paused（暂停，正文保留 7 天）
  └─5 分钟内无法完成 status/messages 对账→ review_required（暂停，正文保留 7 天）

review_required（已有 run_id，且用户明确重新核对）
  ├─读到非终态→ accepted（取得双 lease，conversation 仍保持暂停）
  ├─completed + messages 成功→ done
  └─非成功终态 + messages 成功→ paused
```

终态本地状态：

- `done`：上游 completed 且 messages 对账成功；正文必须为 NULL。
- `paused`：已有 run id 的非成功结果已基本确认；不会重发该 item。
- `review_required`：接纳或结果仍有歧义；不会重发该 item。
- `rejected`：明确没有被 Hermes 接纳；不会原地编辑/重用该 operation。
- `cancelled`：用户取消尚未 dispatch 的 item；正文立即清除。

`paused/review_required/rejected` 都不是“等待再次发送的同一项”。用户只能查看事实、复制恢复正文为一个新草稿或丢弃正文。重新发送新草稿将产生全新的 operation/key，并必须提示可能重复。

## 4. Conversation 队列暂停

conversation 独立保存 `queue_paused` 和 `pause_reason`。以下情况设为 paused：

- upstream `failed`（含 `partial=true`）；
- upstream `cancelled` 或 `interrupted`；
- 用户点击 stop（立即暂停，不等待终态）；
- admission 明确 rejected；
- admission/result 进入 `review_required`；
- completed 但消息对账超过 5 分钟仍不成功。
- 人工重新核对最终确认 completed，但用户尚未明确继续后续队列（`manual_resume_required`）。

后续 `queued` items 原样保留并仍可编辑/取消。只有用户调用“继续队列”，且没有 active item、Hermes healthy，才清除 pause 并尝试 dispatch 当前 FIFO 队首。

如果 paused item 后面没有 queued item，“继续队列”只清 pause，不会重发 paused item。

## 5. Run 双状态模型

```text
local_state:
submitting -> accepted -> reconciling -> reconciled
     ├───────────────→ rejected
     └───────────────→ review_required
accepted/reconciling ─→ review_required

upstream_status（可空，原样保存）：
queued | running | waiting_for_approval | stopping |
completed | failed | cancelled | interrupted
```

规则：

1. `local_state` 与 `upstream_status` 永远分列。
2. `partial` 是布尔附加字段；UI 的“部分完成”通常是 `failed + partial=true`。
3. `interrupted` 可由 status 恢复，不要求存在同名 SSE。
4. terminal SSE 只触发对账，不直接把 run 标成 reconciled。
5. `completed` 必须同时完成 messages 读取和 effective session id 更新，才能成为 `reconciled/done`。

## 6. Operation、幂等与 admission 恢复

### 6.1 不可变字段

queue item 首次创建时生成：

- `operation_id`：本地公开 operation id；
- `idempotency_key`：`ec_` + 随机 UUID，无用户正文；
- `payload_sha256`、`payload_bytes`；
- conversation 与 FIFO 序号。

进入 `dispatching` 时再固定：

- `dispatch_session_id`；
- `first_attempt_at`；
- `admission_deadline_at = first_attempt_at + min(capability retention, 86400 秒)`。

所有 admission 恢复必须使用完全相同的 idempotency key、payload 和 `dispatch_session_id`。任何一个缺失或变化都转人工复核，不能创建“差不多相同”的请求。

### 6.2 自动尝试边界

- 初次请求加最多 3 次恢复尝试，总尝试数最多 4 次；延迟为 1、2、5 秒并尊重安全的 `Retry-After`，但绝不越过 deadline。
- 只有连接错误、超时、408/425/429 或 5xx 且仍无 `run_id` 才允许恢复尝试。
- 400/404/405/413/415/422 等明确未接纳响应进入 `rejected`；401/403 也进入 `rejected`，并把全局连接状态设为 `auth_failed`。
- 409 idempotency fingerprint 冲突进入 `review_required`，绝不更换 key/body/session。
- 一旦任意响应给出有效 `run_id`，立即停止 admission retry，后续仅 GET status/messages。

## 7. 恢复正文生命周期

正文存储规则：

| item 状态 | 是否保留正文 | 到期 |
| --- | --- | --- |
| `queued` | 是 | 无自动 TTL，直到发送或取消 |
| `dispatching/accepted/reconciling` | 是 | active 期间不清除 |
| `done` | 否 | 对账事务中立即清除 |
| `cancelled` | 否 | 取消事务中立即清除 |
| `paused/review_required/rejected` | 是 | 进入该状态起 7 天 |

7 天恢复期内 UI 显示到期时间和两个动作：

- “复制为新草稿”：要求目标 conversation 当前草稿为空或由用户明确覆盖；不改变原 item；显示“再次发送可能重复”。
- “丢弃恢复副本”：立即将正文置 NULL，保留 hash/bytes/run 状态。

清理任务至少每小时扫描到期行，置 `payload_text=NULL`、`payload_expired_at=now`。正文不得写日志、事件或搜索索引。

## 8. 事件接收和本地 SSE

后端每 run 创建一个 in-memory hub：

```json
{
  "local_run_id": "lr_...",
  "local_seq": 17,
  "type": "message.delta",
  "payload": {"delta": "..."},
  "received_at": "2026-09-19T00:00:00.000Z"
}
```

- `local_seq` 是每个 local run 的单调序号，不是 Hermes replay cursor。首次从 1 开始；进程重启后从 SQLite 的 `last_event_seq + 1` 继续，绝不复用旧 id，同时先向浏览器报告 `process_restarted` gap。
- 环形缓冲上限：每 run 512 个事件或编码后 1 MiB，先达到者为准；超限丢最旧事件并标记 gap。
- run 进入 `reconciled` 或终止于 `review_required` 后保留 hub 60 秒供 UI 收尾，然后释放；不能在只收到 terminal event、尚未完成对账时开始计时。
- 不把事件写 SQLite、文件或浏览器持久库。
- 多个浏览器连接共享同一 hub；最后一个浏览器断开也不取消上游 consumer。

浏览器先 GET run snapshot，再以 `Last-Event-ID` 或 `?after=` 订阅。请求游标早于 ring 最早 seq、hub 已重建或事件丢失时，先发送 `stream.gap` 控制事件，客户端放弃拼接旧 delta并重读 status/messages。

## 9. Stop 和 approval

### 9.1 Stop

- stop endpoint 只允许当前 non-terminal run。
- 用户点击后立刻设置 conversation queue paused，run UI 显示 stopping。
- Hermes stop 返回后继续等待 SSE/status 终态；超时不显示已取消。
- 不论最后返回 cancelled、failed 或 completed，都不自动推进后续队列。

### 9.2 Approval

- `waiting_for_approval` 是 active 状态，继续占用全局 slot。
- UI 只允许对当前 pending request 发送一次 `once` 或 `deny`。
- 重复点击、过期 request 或 409 后重读 run snapshot；不假设命令已执行。
- approval 期间浏览器断开不自动 deny，也不自动 approve；后端继续持有上游 run。

## 10. 恢复流程

### 10.1 浏览器重连

1. GET conversation/run/queue snapshot；
2. 若 run active，GET SSE `after=last_seen_local_seq`；
3. 收到 `stream.gap` 时丢弃临时 assistant/tool UI，显示过程缺失提示并等待/读取最终历史；
4. 绝不因 EventSource 重连调用 send endpoint。

### 10.2 emu-chat 后端启动

1. 清理所有已过期 coordinator lease；
2. 探测 Hermes；
3. 扫描 active item，等待旧 lease 过期后由新 owner 取得 global + conversation lease；接管不会要求 active row 消失，也不改变 item 状态；
4. `dispatching` 且无 run id：若 payload/key/session 完整、deadline 未过且总尝试未满 4 次，则按原 key/body/session 继续；否则 `review_required`；
5. `accepted/reconciling` 且有 run id：只读 status，再按终态读取 messages；
6. `review_required/rejected/paused` 只恢复展示，不自动执行；
7. healthy、无全局 active 且 conversation 未暂停时，才 dispatch 最早可发送队首。

进程重启前的 delta/tool 事件视为不可恢复，所有相关 run snapshot 标记 `events_truncated=true`。

### 10.3 Hermes 不可用/重启

- 不删除草稿、队列、run 或恢复正文；
- 不把读取失败投影为空历史；
- 已有 run id 只等待健康恢复后查 status；
- status=`interrupted` 时进入非成功收尾并暂停；
- Hermes 恢复不会自动发送离线期间的草稿。

## 11. 用户可见状态

至少区分：

`草稿`、`等待发送`、`正在提交`、`运行中`、`等待确认`、`停止中`、`正在核对结果`、`已完成`、`部分完成`、`失败`、`已取消`、`已中断`、`提交被拒绝`、`需要人工复核`、`队列已暂停`、`最终状态已恢复但部分过程缺失`、`恢复副本已过期`。

“等待确认”仅指 approval；“需要人工复核”仅指 emu-chat 无法安全判断 admission/result。两者不得复用同一文案或按钮。
